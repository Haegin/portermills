# Porter-Mills Family App

A private family app with a shared calendar, lists (shopping + packing), and wishlists.
Built as a playground — features may be unrelated to one another.

## Repository Layout

```
portermills/
├── .tool-versions  # erlang, elixir, java (asdf or mise)
├── ios/            # Native iOS app (Swift/SwiftUI), project generated by XcodeGen
├── android/        # Native Android app (Kotlin/Jetpack Compose)
└── server/         # Elixir/Phoenix backend
```

## Architecture

### iOS — Swift / SwiftUI

**Why native iOS**: full access to Apple platform APIs, native SwiftUI components,
no bridge overhead. iOS-only features are built here and simply don't exist in Android.

**Key patterns**:
- UI: SwiftUI views + `@StateObject` / `@ObservedObject` ViewModels
- ViewModels that follow a channel topic subclass `LiveViewModel` (in `Shared/Common.swift`),
  which refetches via `load()` whenever the topic reports a change
- Networking: `URLSession` via `APIClient` (snake_case ↔ camelCase via `JSONDecoder` strategy)
- Real-time: `PhoenixSocket` (`URLSessionWebSocketTask`, V2 serializer, heartbeats, auto-reconnect),
  exposing events per feature as Combine publishers
- Auth state + token: `AuthStore` (backed by Keychain)
- Magic-link sign-in: custom URL scheme `portermills://auth?token=…`, handled in `PortermillsApp.onOpenURL`
- Server origin: build setting `API_BASE_URL` (per configuration in `project.yml`), read from Info.plist
- No external dependencies

**Directory structure**:
```
ios/
├── project.yml                  # XcodeGen spec (the .xcodeproj is generated, not checked in)
├── Portermills/
│   ├── PortermillsApp.swift     # @main entry point, deep-link handling
│   ├── ContentView.swift        # Root TabView (authenticated)
│   ├── Info.plist
│   ├── Assets.xcassets
│   ├── Services/
│   │   ├── APIClient.swift      # HTTP client
│   │   ├── PhoenixSocket.swift  # WebSocket client
│   │   └── AuthStore.swift      # Token + user state, Keychain persistence
│   ├── Shared/
│   │   └── Common.swift         # AccountMenu, LiveViewModel, TextPromptSheet, errorAlert
│   └── Features/
│       ├── Auth/                # LoginView, LoginViewModel, AuthModels
│       ├── Calendar/            # CalendarView (month grid), EventEditor, CalendarViewModel, CalendarModels
│       ├── Lists/               # ListsView, ListDetailView, view models, ListModels
│       └── Wishlists/           # WishlistsView, WishlistDetailView, view models, WishlistModels
└── PortermillsUITests/          # End-to-end UI tests against the dev server
```

Swift needs file names to be unique within a target, so model files are named
`<Feature>Models.swift` rather than `Models.swift`.

**Project setup**: `brew install xcodegen`, then `cd ios && xcodegen` and open
`Portermills.xcodeproj`. Re-run `xcodegen` after adding or removing files.

**Distribution**: TestFlight (requires Apple Developer Program, $99/yr).
Alternative without a developer account: AltStore / SideStore (re-signs every 7 days).

### Android — Kotlin / Jetpack Compose

**Why native Android**: Jetpack Compose is first-class on Android, Hilt for DI is
well-supported, all Android-specific features available without bridges.

**Key patterns**:
- UI: Jetpack Compose + Material 3 (dynamic colour on Android 12+)
- Architecture: MVVM with `ViewModel` + `StateFlow`
- DI: Hilt (with KSP)
- Networking: OkHttp (raw, no Retrofit — keeps it lean). `ApiClient.request` runs on
  `Dispatchers.IO`; the inline `get`/`post`/`patch` helpers only touch public members
- Serialization: `kotlinx.serialization`
- Auth state: `AuthDataStore` (backed by Jetpack DataStore), exposed as an `AuthState` StateFlow
- Real-time: `PhoenixSocket` (OkHttp WebSocket, V2 serializer, heartbeats, auto-reconnect),
  connected whenever there is a session; screens collect `socket.events("<feature>")` and refetch
- Magic-link sign-in: `portermills://auth?token=…` intent filter, handled in `MainActivity`
- Navigation: Compose Navigation, one nested graph per bottom-bar tab

**Directory structure**:
```
android/app/src/main/java/app/portermills/
├── MainActivity.kt            # Deep-link handling
├── PortermillsApp.kt          # Hilt @HiltAndroidApp
├── navigation/
│   └── AppNavigation.kt       # NavHost + NavigationBar
├── ui/
│   ├── theme/Theme.kt
│   └── components/Common.kt   # AccountMenu, dialogs, empty state
├── data/
│   ├── api/
│   │   ├── ApiClient.kt       # HTTP client (OkHttp)
│   │   └── AuthDataStore.kt   # DataStore session persistence
│   └── socket/
│       └── PhoenixSocket.kt   # WebSocket client
└── features/
    ├── auth/                  # AuthViewModel, LoginScreen, Models
    ├── calendar/              # CalendarViewModel, CalendarScreen (month grid), EventEditor, Models
    ├── lists/                 # ListsViewModel, ListDetailViewModel, ListsScreen, ListDetailScreen, Models
    └── wishlists/             # WishlistsViewModel, WishlistDetailViewModel, screens, Models
```

**Distribution**: Firebase App Distribution (recommended) or direct APK sideload.
Build: `cd android && ./gradlew bundleRelease`

### Server — Elixir/Phoenix

**Key libraries**:
- Phoenix (HTTP + Channels + LiveView)
- Ecto + Postgrex (PostgreSQL)
- Guardian (JWT auth)
- Swoosh + gen_smtp (magic-link email)
- Jason (JSON)

**Directory structure**:
```
server/lib/
├── mix/tasks/              # mix portermills.add_user
├── portermills/            # Business logic (contexts)
│   ├── accounts/           # Users, families, magic tokens, UserNotifier (email)
│   ├── calendar/           # Calendar events
│   ├── lists/              # Shopping + packing lists, packing-list templates
│   └── wishlists/          # Wishlists (separate context)
└── portermills_web/        # HTTP + WebSocket layer
    ├── broadcast.ex        # REST writes → family channel topics
    ├── channels/           # Phoenix Channels (real-time, receive-only)
    ├── controllers/        # REST endpoints + explicit *_json renderers
    └── live/               # LiveView (web-facing features)
```

**Auth**: there is no sign-up; family members are added with
`mix portermills.add_user NAME EMAIL [--admin] [--family NAME]`. Sign-in is by magic link:
`POST /api/auth/magic-link` emails a link to `/auth/magic/<token>`, a small page that
hands the token to the app via `portermills://auth?token=…`; the app exchanges it at
`POST /api/auth/verify` for a JWT. Only a SHA-256 hash of each token is stored.

**Real-time**: every REST write broadcasts on the family's topic for that feature
(`PortermillsWeb.Broadcast`). Clients join `family:<id>:calendar`, `family:<id>:lists`
and `family:<id>:wishlists` and refetch when something arrives. The channel accepts no
writes. Wishlist payloads carry ids only, and `wishlist:claims_changed` is withheld from
the wishlist's owner in `FamilyChannel.handle_out/3`.

## Feature Domains

### Calendar
Shared family calendar with a month view on both apps. Events broadcast in real time via
Phoenix Channel (`family:<id>:calendar`). All family members see changes immediately.
`GET /api/calendar/events` takes `from`/`to` (ISO 8601) or `year`/`month`.

### Lists
Shopping list and packing lists (multiple named packing lists for different occasions).
Real-time sync via Phoenix Channel (`family:<id>:lists`). Checking off an item on one
device instantly updates others.

Data lives in `lists` + `list_items` tables within the `lists` context. Packing list
templates are stored separately (`list_templates` + `list_template_items`). Creating a
list with a `template_id` copies the template's items; a list can be saved as a template
with `from_list_id`.

### Wishlists
**Intentionally separate** from lists — different UX, different data model, different
Channel. Each family member has their own wishlist. Others can view and mark items as
claimed/purchased without the wishlist owner seeing (for surprise gifts): the claim fields
(`is_claimed`, `claimed_by_me`, `claimed_by_name`) are left out of every response to the
owner.

An owner can also share a read-only public page (`/wishlists/<share_token>`, LiveView, no
claim data) with people outside the family.

Data lives in `wl_wishlists` + `wl_items` + `wl_claims` tables in the `wishlists` context.
No code is shared with the `lists` context (enforced by `test/portermills/separation_test.exs`).

## Data Model (summary)

### Accounts
- `families` — (id, name)
- `users` — (id, family_id, name, email, role: admin|member)
- `magic_tokens` — (id, user_id, token (SHA-256), expires_at, used_at)

### Calendar
- `calendar_events` — (id, family_id, created_by_id, title, description, starts_at, ends_at, all_day, recurrence_rule)

### Lists
- `lists` — (id, family_id, type: shopping|packing, name, archived)
- `list_items` — (id, list_id, name, checked, position, added_by_id)
- `list_templates` — (id, family_id, name)
- `list_template_items` — (id, template_id, name, position)

### Wishlists (separate schema prefix: `wl_`)
- `wl_wishlists` — (id, user_id, is_visible_to_family, share_token)
- `wl_items` — (id, wishlist_id, name, url, notes, price, priority)
- `wl_claims` — (id, item_id, claimed_by_id) — hidden from wishlist owner

## Development

The dev server listens on port **2310** on all interfaces.

### Server
```bash
cd server
mix deps.get
mix ecto.setup   # creates DB, runs migrations, seeds (Admin + Sam, a shopping list, templates)
mix phx.server   # starts on localhost:2310
mix test
```
Dev and test connect to Postgres as your OS user (Homebrew's default superuser);
override with `PGUSER` / `PGPASSWORD` / `PGHOST`.

In dev, magic links are not emailed: each one is written to the server log (including
the `portermills://` app link) and to the local mailbox at
http://localhost:2310/dev/mailbox.

### iOS
```bash
cd ios && xcodegen && open Portermills.xcodeproj
```
Select a simulator and press Run. Debug builds point to `http://localhost:2310`.
To sign in on the simulator, request a link in the app, then open the app link from the
server log: `xcrun simctl openurl booted "portermills://auth?token=…"`.

UI tests drive the main flows against the running dev server. They need a fresh token
from the server log:
```bash
TEST_RUNNER_MAGIC_TOKEN=… xcodebuild test -project ios/Portermills.xcodeproj \
  -scheme Portermills -destination 'platform=iOS Simulator,name=iPhone 16'
```

### Android
```bash
cd android
./gradlew installDebug   # installs on connected device/emulator
```
Debug builds point to `http://10.0.2.2:2310` (localhost from the Android emulator).
Override with `-PdevServerHost=… -PdevServerPort=…`. To sign in, open the app link from
the server log: `adb shell am start -a android.intent.action.VIEW -d "portermills://auth?token=…"`.

### Environment
Production settings are read at boot by `server/config/runtime.exs`. Copy
`server/.env.example` → `server/.env` and fill in `DATABASE_URL`, `SECRET_KEY_BASE`,
`GUARDIAN_SECRET`, and the Fastmail SMTP credentials. The planned production host is
`api.portermills.net` (behind a Cloudflare tunnel), sending mail as `app@portermills.net`.

## Conventions

- All new server-side features go in their own context under `server/lib/portermills/<name>/`.
- Every server read and write is scoped to the caller's family; `family_id` and
  ownership fields are set by the context, never cast from request params.
- iOS features live in `ios/Portermills/Features/<Name>/`; Android features in
  `android/.../features/<name>/`. Feature structure is ViewModel + Screen(s) + Models.
- Android-only features simply don't have a counterpart in `ios/`, and vice versa.
- Web-accessible features (visible to non-family users) are built in LiveView under
  `portermills_web/live/` and protected by separate auth logic.
- Wishlists data MUST NOT be imported or referenced from the lists context, and vice versa.
- API field names are snake_case on the server. iOS uses `JSONDecoder.keyDecodingStrategy = .convertFromSnakeCase`.
  Android uses `@SerialName` annotations on model fields.
